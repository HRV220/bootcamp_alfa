Дата анализа: 14.11.2026. Папка `night` исключена. Проверены [паспорт](case3_selection_and_hypothesis.md), [ноутбук](case3.ipynb), сохранённые вход/ответы, [бэклог кейса](case_3_backlog.md), [lineage](lineage1.1.png) и SQL событий [из папки case2](../case2/stage.sql). Новых запросов к LLM и кластеру не выполнялось.

**Вывод: техническая возможность получить связный русский обзор из структурированных событий подтверждена демонстрацией. Цель «фактически корректное саммари с сохранением хронологии» на сохранённом примере не достигнута. Снижение выдуманных событий за счёт проверки фактов не проверено.**

## Ожидания и критерии

Гипотеза 1: структурированных фактов достаточно для полезного связного обзора ключевых эпизодов. Гипотеза 2 из [общей постановки](../selected_cases.md): проверка фактов снижает риск выдуманных событий.

По паспорту результат должен содержать только подтверждённые факты, корректные таймкоды и стадии, единый формат. Для полноты нужен заранее определённый список обязательных фактов; для полезности — согласованный способ оценки. Наличие текста само по себе закрывает только техническую генерацию.

## Проверка целостности первого ответа

Сравнение входного JSON и JSON ответа проведено программно:

| Проверка | Результат |
|---|---:|
| Число входных событий | 181 |
| Число выходных описаний | 181 |
| Уникальных ID в ответе | 180 |
| Позиции, где ID ответа отличается от входного | 4 из 181 |
| Входные ID, отсутствующие в ответе | 4 |
| ID ответа, которых нет во входе | 3 |
| Повторяющиеся ID ответа | 1 значение |

Четыре несовпадения расположены на позициях **17, 29, 46, 110** при отсчёте с нуля. Например, покупка Axe на 7:01 имеет исходный ID `purchase:6af7fdde2652c8d2ed622f4c`, но в ответе указан `purchase:6af7fdde2652c8d2ed622f4a`. На позиции 46 корректный таймкод 657 секунд = 10:57 заменён текстом «На 11: -»; на позиции 110 вместо 1250 секунд = 20:50 получено «На 21: -».

Доля позиционных несовпадений ID — `4 / 181 = 2,21%`. **Это показатель нарушения контракта идентификаторов, а не доля фактических ошибок всего саммари.** Не все ошибки ID означают ошибку содержания; факт ошибок содержания оценивается отдельно.

Парсер проверяет JSON и наличие массива, но не проверяет точное соответствие ID. Во второй запрос описания присоединяются через `zip(source_events, first_events)` по позиции, без сверки ID. В сохранённом примере длины равны, поэтому обрезания нет, однако при разной длине `zip` пропустит хвост молча. Вновь присвоенный исходный ID не исправляет неправильное описание.

## Почему целевой результат не проходит проверку

| Проверяемое требование | Исходное доказательство | Нарушение в итоговом тексте |
|---|---|---|
| Точное время убийства | Во входе Queen of Pain убивает Axe на 311-й секунде = 5:11 | Итоговый обзор утверждает 5:16; на 5:16 во входе Witch Doctor убивает Dragon Knight |
| Корректные стадии | Промпт: лейнинг <600 сек., ранняя игра 600–1499 сек., средняя с 1500, поздняя с 2400 | Во втором абзаце «ранней игры» описаны 6:59, 7:15 и 8:23; события до 24:52 названы средней и поздней игрой |
| Только известная география | Во входе нет координат/линий столкновений | Обзор добавляет «в окрестностях мидов и лесных стыков» |
| Причинные выводы должны подтверждаться | Во входе есть покупки и убийства, нет данных о применении предметов | Покупками объясняется, «почему обмены так быстро накатывали друг за другом» |
| Завершение матча должно подтверждаться | Нет результата матча, времени окончания или события падения трона | После башен на 24:52 объявлено, что «игра фактически завершилась» |

Для данного входа допустимы только лейнинг и ранняя игра по правилам самого промпта. Добавление средней и поздней стадий — проверяемая ошибка формата и хронологии. Оговорка текста, что победитель неизвестен, полезна, но не подтверждает утверждение о фактическом завершении игры.

Во второй запрос передаются только `event_id`, `type`, `time`, `description`. Исходные поля героев, предметов, чисел и команд отсутствуют, хотя промпт предписывает опираться на структурированные факты. Это ослабляет возможность сверки и позволяет ошибкам первого этапа перейти в итоговый текст.

## Статус гипотез и целей

| Гипотеза/цель | Статус | Почему |
|---|---|---|
| Преобразовать структурированные события в связный русский текст | Продемонстрировано на одном матче | Сохранены вход, описания и итоговый обзор |
| Получить полезное саммари при сохранении фактов | Подтверждена только техническая часть; целевое качество не достигнуто | Есть конкретные ошибки времени, стадий и неподтверждённые утверждения; полезность не оценена экспертами |
| Проверка фактов снижает риск выдуманных событий | Не проверено | Два генеративных вызова не являются сравнением с верификатором и без него; отдельного проверяющего этапа и эксперимента нет |
| Полнота и единый формат | Не закрыто | Полнота по обязательным фактам не измерена; стадии нарушены |
| Воспроизводимое эксплуатационное решение | Частично | Есть код/outputs/lineage; нет полного журнала версий входа, параметров, стоимости, задержки, проверок и SLA |

Один неуспешный по качеству пример не опровергает принципиальную возможность полезной генерации. Он опровергает утверждение, что сохранённый результат уже удовлетворяет требованию отсутствия неподтверждённых фактов. Общая доля фактических ошибок и полнота не рассчитаны: для них нужна разметка всех утверждений и обязательных эпизодов, а не только поиск нескольких контрпримеров.

## Итог для отчёта и что нужно закрыть

**Формулировка результата:** «Создан прототип двухэтапной генерации обзора: из 181 события матча получены описания и связный русский текст. Демонстрация подтверждает работоспособность подхода к генерации. Проверка выявила ошибки идентификаторов, времени, стадий и неподтверждённые выводы; целевое качество саммари пока не достигнуто».

Для полного закрытия: передавать исходные поля вместе с описаниями; валидировать длину, уникальность и точное соответствие ID; связывать по проверенным ID; вычислять таймкоды и стадии программно; запрещать выводы об исходе без данных матча; проверять итоговые утверждения. Затем зафиксировать контрольный набор матчей, обязательные факты и критерии полезности и сравнить один и тот же генератор с проверкой фактов и без неё. Измерить долю ошибок, полноту и полезность, сохранив версии и параметры.

Числа, ID и порядок входа независимо пересчитываются скриптом [verify_evidence.py](../analysis/verify_evidence.py). Скрипт читает сохранённые outputs и не вызывает LLM.
