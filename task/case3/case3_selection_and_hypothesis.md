# Паспорт кейса 3: саммари матча

**Направление:** LLM №24. Актуализировано: **14 ноября 2026 года** по коду и сохранённым результатам проектного ноутбука.

**Цель:** автоматически создавать короткий послематчевый обзор Dota 2 на русском языке по структурированным событиям, сохраняя факты и хронологию.

**Гипотеза 1:** структурированных фактов о матче достаточно для связного и полезного обзора ключевых эпизодов.

**Гипотеза 2:** проверка фактов снижает число выдуманных событий и ошибочных выводов. Для её проверки требуется сравнение вариантов с проверкой и без неё на одном наборе матчей; текущий ноутбук такого эксперимента не содержит.

| Параметр | Определение |
|---|---|
| Объект | Один матч Dota 2 с доступной историей событий |
| Единица анализа | Один обзор матча; для проверки фактов — отдельное утверждение обзора и исходное событие |
| Реализация | [case3.ipynb](../task/case3/case3.ipynb) |
| Демонстрационный матч | `match_id = 9045752693` |
| Период данных | События выбранного матча; календарный период и версия RAW в ноутбуке не зафиксированы |
| Источники событий | `lakehouse.raw.mongo__kill_events`, `mongo__tower_death_events`, `mongo__gold_events`, `mongo__buyback_events`, `mongo__purchase_events`, `mongo__streak_events` |
| Справочники и участники | `lakehouse.raw.pg__items`, `pg__heroes`, `pg__match_players` |

| Покупки | Только предметы с известной записью справочника и стоимостью строго больше 2 000 |
| Сортировка | Игровое время в секундах, затем `event_id`; события без времени — в конце |
| Привязка игрока | `steam_account_id` события ↔ `account_id` участника внутри выбранного матча; герой подставляется только при однозначном соответствии |
| Анонимные аккаунты | Для ID `0` и `4294967295` имя героя по аккаунту не восстанавливается; остальные доступные факты сохраняются |
| Этап 1 LLM | Для каждого события — одно короткое описание на русском в JSON с исходным `event_id` |
| Этап 2 LLM | Связный текст обзора по описаниям событий, сгруппированный по стадиям игры |
| Модель | В обоих вызовах указана `openai/gpt-5.4-nano` через настроенный OpenAI-совместимый endpoint |
| Формат результата | Русский текст, один абзац на непустую стадию, обычно 2–4 предложения; ключевые таймкоды в формате М:СС |
| Основная метрика качества | Доля неподтверждённых или противоречащих входу фактических утверждений среди всех проверенных утверждений |
| Дополнительные метрики | Доля отражённых обязательных фактов, корректность таймкодов и стадий, соответствие формату, экспертная полезность |
| Целевое требование | Ни одного неподтверждённого факта; каждый упомянутый герой, предмет, число, исход и таймкод должны иметь опору во входе. Это требование, а не измеренный результат |
| Глубина и обновление | Один матч целиком в пределах выбранных типов событий, ручной запуск по `match_id`. Расписание, SLA, срок хранения и лимиты стоимости не настроены |

**Критерий успеха по целевой метрике:** обзор содержит только подтверждённые факты, правильно относит события к стадиям и соблюдает заданный формат. Полноту оцениваем по списку обязательных фактов, заранее размеченному для каждого контрольного матча; пересказ всех событий не требуется. Численные пороги полноты и полезности в проекте не согласованы.

**Кейс выполнен**, когда извлечение фактов и генерация воспроизводятся, обзор сопоставлен с исходными данными, измерены ошибки и полнота, сделан вывод о полезности и ограничениях. Для подтверждения второй гипотезы дополнительно нужен сравнительный эксперимент.

## Ограничения

- Обзор описывает только выбранные источники и события. Отсутствие события в выгрузке не означает, что его не было в игре. Награда из `gold_events` с `reason = 'roshan'` сама по себе не подтверждает всю историю контроля Рошана.
- Порог стоимости покупки не гарантирует, что это законченный или действительно ключевой предмет. Предметы без справочника и покупки стоимостью до 2 000 не попадают во вход.
- Маски башен сохраняются без расшифровки: по ним нельзя утверждать сторону, линию, тир или падение трона. Победитель, итоговый счёт и длительность из `pg__matches` сейчас не извлекаются; `match_result` и подтверждённая первая кровь не формируются.
- Двухэтапная генерация может переносить ошибки первого ответа в итоговый обзор. Во второй запрос передаются только `event_id`, `type`, `time` и сгенерированное описание; исходные поля героя, предмета, команды и чисел теряются, хотя промпт требует опираться на них.
- Парсер первого ответа проверяет корректность JSON и наличие массива `events`. Проверки количества, уникальности, порядка и соответствия `event_id`, содержания описаний и фактической точности нет. `zip` связывает события по позиции и при разной длине молча обрезает массив.
- Требования промпта не обеспечивают автоматическую валидацию. Повторные ответы могут отличаться; версии среза и промптов, параметры генерации, задержка и стоимость вызовов отдельно не журналируются.
- В репозитории сохранён один пример. Он позволяет показать работу прототипа, но не оценить качество на разных матчах и не подтвердить снижение числа ошибок благодаря проверке фактов.

## Условия подготовки фактов и генерации

1. Выбрать `match_id`; Spark SQL объединяет события через `UNION ALL`. Для покупок добавляются название и стоимость из справочника; из streak-событий выбираются `KILL_STREAK` и `MULTI_KILL`.
2. Подставить имена героев по `hero_id`. Аккаунт сопоставлять с героем только при однозначной связи в этом матче. Сторону убийства определять лишь при известных и противоположных сторонах атакующего и цели.
3. Сформировать `match_payload` с `match_id` и массивом событий, упорядоченным по времени и ID. Сохранять только известные поля; неизвестная сторона убийства остаётся `null`. Пустая выборка останавливает текущий процесс.
4. Первый LLM-вызов возвращает JSON с кратким описанием каждого события. До передачи дальше требуется проверять соответствие исходным ID, полноту массива, героев, числа и таймкоды; сейчас реализован только разбор структуры JSON.
5. Второй LLM-вызов формирует обзор. Для проверяемого результата ему нужно передавать исходные структурированные факты вместе с описаниями и проверять текст после генерации; текущий код передаёт сокращённый набор полей.

Правила стадий из текущего промпта:

| Стадия | Время события |
|---|---|
| Лейнинг | `0 <= time < 600` — до 10:00 |
| Ранняя игра | `600 <= time < 1500` — от 10:00 до 25:00 |
| Средняя стадия | `1500 <= time < 2400` — от 25:00 до 40:00 |
| Поздняя игра | `2400 <= time <= 3900` — от 40:00 до 65:00 включительно |
| Гиперлейт | `time > 3900` — после 65:00 |

Пустые стадии пропускаются; важные события без времени описываются отдельно, предматчевые — перед лейнингом. Для сохранённого входа допустимы только лейнинг и ранняя игра. Победитель, первая кровь, применение предмета и причинные связи упоминаются лишь при прямом подтверждении; при отсутствии результата обзор заканчивается последним подтверждённым эпизодом.

**Статус ETL:** чтение RAW и подготовка JSON реализованы в ноутбуке; сохранены результаты генерации. Отдельные Iceberg-таблицы STAGE/MART, автоматическое обновление, lineage и публикация обзоров этим артефактом не подтверждены. Для повторной проверки следует сохранять входной JSON, оба ответа, версию промптов и отчёт валидации для каждого матча.
