# MART кейса 1 — Доминатор и винрейт

Витрины строятся на готовом STAGE из `../stages/`. Файлы `stages/R/` не используются. STAGE не изменяется.

## Входы и порядок создания

В портале выбери слой **MART**, режим **SQL**. Имя таблицы указывай без `lakehouse.mart`, SQL вставляй целиком из соответствующего файла. Запросы содержат один `WITH/SELECT`; создание и запись таблиц выполняет портал.

| Порядок | Имя таблицы | SQL | Одна строка |
|---|---|---|---|
| 1 | `case1_dominator_first_purchase` | [dominator_first_purchase.sql](dominator_first_purchase.sql) | Покупатель в матче |
| 2 | `case1_dominator_winrate` | [dominator_winrate.sql](dominator_winrate.sql) | Сравнение ранней и поздней групп по всему срезу |

Вторая таблица создаётся после успешного заполнения первой.

Зависимости:

```text
lakehouse.stage.matches ─────────┐
lakehouse.stage.match_players ───┼─> lakehouse.mart.case1_dominator_first_purchase
lakehouse.stage.purchase_events ┘                       │
                                                       └─> lakehouse.mart.case1_dominator_winrate
```

Имя `lakehouse.stage.matches` взято из зависимостей действующих STAGE-запросов. Если таблица в портале названа `matches_fixed`, замени только этот вход в SQL первой витрины. У покупок используется колонка `itemId`, как в текущем STAGE. Справочник предметов не нужен для расчёта: ID Доминатора `164` задан паспортом.

## Первые покупки

Правила взяты из [case_definition.md](../case_definition.md):

- Сначала считаем все события предмета `164` на `(match_id, steam_account_id)`, затем применяем допуск пары. Один или два события допустимы; больше двух исключают всю пару.
- Сопоставление с участниками должно давать ровно одну строку. Аккаунт `0` исключается; `4294967295` сохраняется при однозначном сопоставлении. NULL ранга сохраняется.
- Для анализа требуются известные герой, сторона, исход, режим и лобби. Исключаем лобби `1, 4, 8`, режимы `15, 18, 19, 20, 21, 23`; исход участника сверяем с победителем матча.
- Если у любого доступного события пары время отсутствует, отрицательно или выходит за длительность матча, исключается вся пара. Проверки выполняются до выбора первой покупки.
- Первое время — минимум секунд от начала матча. После всех проверок и фильтров нужно рассчитать медиану первых времён по одной строке на покупателя в матче. `early` — время не больше медианы, `late` — больше. Минута хранится без округления.
- `is_provisional = true`, `history_complete = NULL` отражают статус полноты истории из паспорта.

Ключ результата — `(match_id, steam_account_id)`. `player_slot`, `hero_id`, `rank`, режим, лобби и длительность сохраняются для анализа срезов в Jupyter и Superset.

SQL рассчитывает точную медиану через упорядочивание допущенных наблюдений: центральное время при нечётном количестве строк и среднее двух центральных при чётном. Значение сохраняется в `median_purchase_time_sec` и `median_purchase_minutes`; оно единое для всего среза и определяется до расчёта винрейтов. При одинаковых временах на границе все они относятся к `early`, поэтому равенство размеров групп не гарантируется. На пустой выборке медиана равна NULL. Фактическое значение медианы текущей выборки в кластере ещё нужно рассчитать.

Период **14–15 октября 2026 UTC** задаётся готовым входным срезом, указанным в паспорте. Текущий STAGE матчей не передаёт `start_time`, поэтому MART не фильтрует даты самостоятельно и не рассчитывает абсолютное Unix-время покупки. `mart_loaded_at` обозначает время расчёта, а не время матча.

## Винрейты и целевой эффект

`early_win_rate` и `late_win_rate` — доли от 0 до 1; поля с суффиксом `_pct` — проценты от 0 до 100. `win_rate_diff_pp` — ранний винрейт минус поздний, в процентных пунктах. `target_reached` показывает достижение разницы **+3 п.п.** на доступном срезе, без утверждения о статистической значимости или причинном эффекте.

Знаменатель винрейта — число покупателей, а не число матчей. Матч может входить в обе группы, поэтому `early_matches_count + late_matches_count` может превышать `matches_count`.

При отсутствии одной из групп её винрейт, разница и `target_reached` равны NULL. На пустом входе сводка возвращает одну строку с нулевыми счётчиками и NULL метрик сравнения.

Для фильтруемых графиков используй детальную витрину: `timing_group` как группу, `COUNT(*)` как число наблюдений, `AVG(CASE WHEN win THEN 1.0 ELSE 0.0 END)` как винрейт. Порог медианы при фильтрации графиков не пересчитывается. Сводная витрина сохраняет рассчитанный порог и предназначена для KPI всего среза; фильтры по героям и режимам к ней не применяются.

Статистическую неопределённость нужно оценивать отдельно с учётом зависимости покупателей одного матча.

## Обновление

Полная пересборка после обновления входного STAGE: сначала первые покупки, затем сводка. Требование паспорта — раз в час при изменении входов, для неизменного среза достаточно одной сборки. Хранение — до конца буткемпа и 30 календарных дней после защиты. Расписание и хранение настраиваются в портале отдельно.

`source_mart_loaded_at_min/max` в сводке сохраняют временные метки прочитанной детальной витрины. После обновления первой таблицы сводку нужно пересобрать; эти две записи не являются общей транзакцией.

Файлы подготовлены для загрузки в портал; выполнение в Spark/Trino и создание таблиц в кластере не выполнялись.
