## ppt/slides/slide11.xml
Lakehouse: таблицы поверх масштабируемого хранения
Data Lakehouse /  — архитектурный подход, объединяющий масштабируемое хранение Data Lake с возможностями управления таблицами, характерными для Data Warehouse
COMPUTE / Spark / Trino / Flink / SQL engines
TABLE FORMAT / Iceberg / Delta Lake / Hudi
STORAGE / Object Storage / файловое хранилище
Что добавляет табличный слой
Атомарные изменения таблиц / Контроль и развитие схемы / Метаданные о файлах / Согласованное чтение и запись / Версионирование и снимки / Возможность отката / Оптимизация чтения данных
Apache Iceberg /  — открытый табличный формат для крупных аналитических наборов, а не самостоятельная база данных или физическое хранилище. Он поддерживает эволюцию схемы, скрытое партиционирование, time travel, rollback и атомарные изменения таблиц
Важная оговорка. /  Lakehouse — это не «папка с Parquet» и не название одного продукта. Это комбинация хранения, табличного формата, вычислительных движков, каталога и процессов управления

Database /  — база данных
Collection /  — коллекция документов
Document /  — запись с полями и значениями
BSON /  — формат хранения документов

{ /   "_id" / : "...", /   "match_id" / : "...", /   "event_type" / : "...", /   "event_time" / : "...", /   "payload" / : { /     "..." / : "..." /   } / }
Вложенные данные
Связанные данные вложены в один документ / Преимущества:  / чтение одним запросом; данные хранятся вместе / Ограничения:  / повторение данных; рост документа; сложность частичных обновлений
Связи по идентификаторам
Документ содержит идентификатор связанной сущности. / Плюс: /  сущность можно хранить и обновлять отдельно. / Ограничение: /  для получения связанных данных нужен дополнительный запрос или  / $lookup / .

S3: объектное хранение данных
S3 хранит объекты в бакетах и предоставляет к ним доступ по ключу
Основные понятия
Bucket —  / контейнер для объектов
Object —  / данные и метаданные
Key —  / имя объекта, уникальное внутри бакета
Prefix —  / начало ключа для группировки объектов
Metadata  / —  / сведения об объекте
API —  / способ программного доступа
S3 или S3-совместимое хранилище / Bucket / ├──  / raw/ / │   ├── source_a/ / │   └── source_b/ / ├──  / stage / / / └──  / mart / /
Что можно хранить
■  / CSV
■  / JSON
■  / Parquet
■  / Архивы
■  / Логи
■  / Изображения
■  / Результаты выгрузок
■  / Файлы аналитических таблиц
Как устроен доступ
Нет каталогов, как в локальной ФС / Иерархию имитируют префиксами ключей / Объект читают и пишут как единицу / Доступ — через API и совместимые инструменты
От объектов к таблицам
S3 — хранит объекты / Parquet — задаёт формат файлов данных / Iceberg — описывает таблицу, её файлы и снимки / Каталог — помогает находить таблицы и их метаданные / Вычислительный движок — читает данные и выполняет запросы
Роль в буткэмпе
Храним файлы Raw, Stage и Mart / Разделяем данные по слоям и источникам / Сохраняем исходные выгрузки для повтора / Передаём данные между этапами ETL

Raw → Stage → Mart описывает подготовку данных, а не устройство бакета.

## ppt/slides/slide47.xml
ClickHouse: колоночная аналитическая СУБД
ClickHouse — пример СУБД для аналитического чтения и агрегаций по большим наборам данных
Строки и столбцы
Строковое хранение
row 1: id, time, hero, kills, win
row 2: id, time, hero, kills, win
row 3: id, time, hero, kills, win
Колоночное хранение
id: / ... / ...
time: / ... / ...
hero: / ... / ...
kills: / ... / ...
win: / ... / ...
Почему это полезно
Читаются только нужные столбцы / Однотипные значения лучше сжимаются / Эффективны сканирование и агрегации / Рассчитан на аналитику по большим наборам строк
SELECT /     event_type, /     count()  / AS /  events / FROM /  events / GROUP BY /  event_type / ORDER BY /  events  / DESC / ;
Особенности
SQL-интерфейс / Колоночное хранение / Векторизованное выполнение / Семейство движков MergeTree / Партиционирование / Sorting key / Разреженный primary index / Материализованные представления / Распределённое выполнение
Важные оговорки
Не прямая замена PostgreSQL для всех сценариев: ориентирован прежде всего на OLAP / Частые точечные изменения строк — не основной сценарий / PRIMARY KEY в MergeTree — не ограничение уникальности / Sorting key сильно влияет на чтение; партиционирование его не заменяет / Больше индексов — не значит быстрее запросы
