Рекомендуемый темп: около 8–10 минут. Подробные оговорки ниже можно использовать для ответов на вопросы.

## 1. Анализ данных Dota 2

Два кейса текущей защиты: SQL про Helm of the Dominator и ML №18. Название команды в team.md не задано, поэтому не придумано. Состав и роли: requirements/team.md. Третий кейс LLM №24 из selected_cases.md не входит в текущую защиту по уточнению пользователя «оба кейса».

## 2. Задача

Бизнес-сценарии сформулированы на основе целей кейсов, это не подтверждённые интервью с внешним заказчиком. Выгода первого кейса — корректное сравнение таймингов, второго — приоритизация ручной проверки. Причинный эффект покупки и автоматическое наказание игроков не заявляются.

## 3. Бизнес-вопрос и гипотезы

SQL: единица анализа — покупатель в матче, не событие покупки. Точная медиана очищенной выборки, ранние <= медианы, поздние >. +3 п.п. — целевой эффект, не полученный результат. SQL-гипотеза ассоциативная. ML peers, оценка top-K и сравнение ложных тревог являются предложением, а не выполненным экспериментом.

## 4. Данные и связи

Источники: requirements/Источники. Описание полей таблиц.md; task/case1/data_model.md; task/case2/smurf_players.csv. Связи покупок показаны как логические, наличие совпадений не гарантировано. Число соответствий проверяется до JOIN: нельзя восстанавливать сторону покупателя только по match_id. Анонимный ID 4294967295 допустим только при однозначной привязке к участнику. CSV не связан с SQL-срезом доказанным периодом. Полностью пустые поля: rank, calibration, rank_known, tier, kda_c, farm_pos, perf_z. heroes — необязательный справочник, отсутствие имени не удаляет наблюдение. Предлагаемая доработка: quarantining целой пары при любом невалидном событии до min(time).

## 5. Архитектура и паспорта витрин

Физическая целевая схема: PostgreSQL/MongoDB → Airflow → Spark → Iceberg/MinIO (RAW/STAGE/MART) → Trino → Superset. Lineage SQL: raw.mongo__purchase_events + raw.pg__matches + raw.pg__match_players + raw.pg__items → stage.case1_dominator_purchase_events → stage.case1_dominator_first_purchase → mart.case1_dominator_first_purchase → mart.case1_dominator_winrate → графики тайминга и ΔWR. Имена STAGE целевой версии взяты из data_model.md, наличие именно этих объектов надо сверить с кластером, поскольку текущие stages/*.md используют иные имена. ML: CSV → player-match features → profile account/window → score (проект), текущая локальная сводка не является ML-витриной. Предложенный SLA требует измерения: готовый снимок+30 минут, для ML файл+1 час; не гарантия выполнения. SQL хранение и часовой пересчёт — требования паспорта. Полная замена таблиц, согласованные snapshot/run_id, проверки до публикации.

## 6. ETL и контроль выполнения

Скриншоты оставлены по разрешению пользователя, они не имитируют интерфейс. Пользователь сообщил: «есть созданные stage». Это подтверждение наличия STAGE вообще со слов команды, но не наличия именно двух кандидатных потоков таблицы. Существующие task/case1/stages используют matches_fixed, match_players, purchase_events. Предлагаемые night/analysis/case1_sql сохраняют DQ до MIN и требуют отдельной проверки/создания в тестовой зоне. SQL пишется в UI, DAG создаётся платформой, команда проверяет статус/логи/перезапуск. Предложение: фиксированный срез вместо непроверенного инкремента. Для RAW incremental watermark src_modified_stamp можно вводить только после проверки поздних изменений. Идемпотентность: повторная полная сборка из того же snapshot даёт тот же набор бизнес-строк, техническая метка запуска может отличаться. Обнаружены расхождения: matches_fixed vs stage.matches, loaded_at vs sys_insert_stamp, отбрасывание ошибочных событий перед MIN. Они требуют проверки в кластере. Экран SQL и DAG следует вставить без уменьшения до нечитаемости. Таблица потоков описывает логические потоки, не подтверждённый счётчик DAG.

## 7. Аналитика: проверка гипотез

Для SQL до проверки фиксируем период [2026-10-14 00:00 UTC, 2026-10-16 00:00 UTC), фильтры режима/лобби и снимок. Точная медиана по одному покупателю в матче до сравнения WR. ΔWR выражен в процентных пунктах. Bootstrap следует кластеризовать по match_id, потому что покупатели одного матча зависимы. В каждой реплике повторяем оценку медианы; алгоритм и seed фиксируются до результатов. 95% ДИ и число повторов — предлагаемый протокол, не исполненный тест. +3 п.п. — практический порог; ДИ и практическую значимость показываем отдельно. Не допускаем причинного вывода из наблюдательной связи и учёта выживания до поздней покупки. Для ML роль/ранг могут объяснять показатели, а случайный split строк одного аккаунта даёт утечку.

Четыре вывода опираются на подтверждение пользователя, паспорт SQL-кейса и пересчитанный CSV. ## 10. Рекомендации и развитие

Рекомендации прямо следуют из выявленных пробелов. Исправления SQL и проверки синтетических краевых случаев помещены в night/analysis, исходники task не менялись. Они являются кандидатом для тестового запуска, а не внедрением. Следует сверить названия реальных STAGE с проектной схемой и не публиковать витрины до DQ. Организационный вопрос: подтвердить у организаторов зачёт кастомного Доминатора как обязательного основного SQL-кейса. План ML требует источника роли, репрезентативного контроля, истории и независимой разметки.
