## Реализованный путь данных

Spark SQL читает RAW напрямую. Через UNION ALL объединяет шесть источников: kill_events, tower_death_events, gold_events (только reason=roshan), buyback_events, purchase_events, streak_events. Справочники items и heroes, участники match_players обогащают события. События без исходного id не выбираются. Покупки допускаются только при наличии справочника и cost>2000. В streak остаются KILL_STREAK и MULTI_KILL.

Внутри выбранного матча аккаунт связывается с героем только при одном hero_id. Для 0 и 4294967295 восстановление имени по аккаунту отключено. Сторона убийства определяется только при известных разных командах attacker/target. Семантику этих исходных числовых ID всё равно нужно сверить с реальной схемой: код трактует их как hero_id.

Факты сортируются по time, затем event_id, формируется JSON. Первый LLM-вызов должен вернуть одно описание на событие с сохранением event_id. Второй строит обзор по стадиям. В обоих вызовах указан `openai/gpt-5.4-nano` через OpenAI-совместимый клиент. Это значение модели в коде, а не независимое подтверждение конфигурации backend.

Критичный дефект: второй payload строится позиционным `zip(source_events, first_events)`. В него передаются исходные event_id/type/time и сгенерированное description, но не исходные hero/item/team/gold/xp. Промпт требует доверять структурированным фактам, которых в этом payload уже нет. Парсер проверяет только JSON и массив events, не количество/ID/уникальность/факты. Двухэтапная генерация сама по себе не является проверкой фактов.

Метод: JSON разобран из stdout, входные и выходные event_id сопоставлены по позиции и множествам. Для таймкода использовался шаблон `(?<!\d)(\d+):(\d{2})(?!\d)`, затем минуты*60+секунды сравнивались с source.time. Последняя проверка говорит только о распознанных таймкодах, **не является оценкой фактической точности текста**. Наличие одинаковой длины массивов не доказывает правильное соответствие. Четыре изменения ID не следует автоматически называть перестановкой событий: часть ID модель исказила.

## Обнаруженные ошибки итогового обзора

- Сохранены четыре абзаца, включая среднюю и позднюю стадии. Вход заканчивается на 24:52, а по правилам самого промпта средняя начинается с 25:00, поздняя с 40:00. Эти стадии во входе пусты и должны пропускаться.
- Абзац «В ранней игре» ссылается на 6:59, 7:15 и 7:47, хотя это лейнинг по собственным границам промпта.
- Конкретное расхождение: обзор говорит «На 5:16 Queen of Pain также закрыла Axe». В исходном hero_kill Queen of Pain→Axe time=311, то есть **5:11**; первое описание также содержит 5:11. Ошибка возникла при итоговой генерации.
- Обзор добавляет места столкновений — мид/лес — без координат в payload. Приписывает покупкам объяснение темпа и причинное влияние без соответствующих фактов.
- Обзор заявляет, что игра «фактически завершилась разрушениями последних внешних укреплений». Вход содержит только сырые tower masks, без match_result, победителя, длительности и факта падения трона. Последнее известное событие на 1492 секунде — tower_destroyed с radiant_mask=131071, dire_mask=7. Эти поля не устанавливают исход игры.
- Локальная проверка показывает наличие ошибок. Доля неверных утверждений, полнота обязательных фактов и полезность систематически не измерены. Нельзя писать «0 галлюцинаций», «качество 97,8%» или «гипотеза подтверждена» по проверке ID.

## Метрики и честный вывод для слайдов

**Гипотеза 1:** генерация связного русскоязычного текста из событий продемонстрирована на одном матче. Полезность при соблюдении фактов не подтверждена; сохранённый обзор содержит проверяемые ошибки.

**Гипотеза 2:** снижение числа ошибок после fact-checking **не проверено**. Нет отдельного проверяющего этапа и парного эксперимента с/без него на одном контрольном наборе. Два вызова «описание → обзор» не являются таким экспериментом.

Предлагаемые метрики: доля неподтверждённых/противоречащих входу утверждений; покрытие размеченных обязательных фактов; корректность таймкодов и стадий; соблюдение формата; экспертная полезность. Фактических агрегатов этих метрик по контрольному набору нет. Нулевые ошибки — целевое требование, а не достигнутый KPI.

Для слайда результатов уместны KPI **1 матч / 181 событие / 2 LLM-вызова**, фрагмент правильного описания и рядом конкретная ошибка итогового обзора. Для слайда качества — **4 несовпадения ID и 13 неполных таймкодов**, обязательно подписать «локальный аудит сохранённого примера».

## Что нужно до эксплуатационной готовности

1. Валидировать схему, количество, уникальность, точное множество и порядок event_id. Связывать по ключу, не zip; останавливать pipeline при нарушении.
2. Передавать второму этапу исходные факты. Проверять итог по фактам, времени и стадиям, запретить неподтверждённый финал. При ошибках использовать извлекательный fallback.
3. Сохранять вход, оба ответа, hash/версию промпта, модель, snapshot/run_id, задержку и стоимость. Сейчас нет зафиксированного календарного периода/версии RAW.
4. Подготовить разнообразный контрольный набор с обязательными фактами и независимой разметкой. Сравнить варианты с/без проверки на одинаковых матчах.
5. Связать подтверждённый UI-граф events_match с фактической генерацией и сохранением итогов. Выделенные STAGE/MART для JSON/описаний/обзора, DAG, SLA, retention и стоимость текущим ноутбуком не подтверждены.
