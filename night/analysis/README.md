## Фактическое профилирование ML CSV

Из корня проекта:

```powershell
python night/analysis/profile_smurf.py
```

Скрипт читает только `task/case2/smurf_players.csv`, сохраняет `smurf_profile.json` и `smurf_account_summary.csv` рядом с собой. В JSON есть SHA256 источника, пропуски, ключи, распределения и арифметическая проверка KDA/hd_pm/lh_pm. Это фактически выполненная описательная аналитика 87 наблюдений, а не обучение модели. Присвоение `smurf=1` взято из файла, способ получения меток неизвестен. Значение 88,5% означает 77 побед из 87 выбранных строк, а не precision или «точность определения смурфов».

## Предлагаемые исправления SQL кейса 1

Папка `case1_sql/` содержит самостоятельные SELECT-запросы. В них **нет CREATE/DROP/DELETE/записи в общий RAW**. Они предназначены для создания новых проектных таблиц через портал после проверки владельцем среды. В кластере они не выполнялись. Пакет обеспечивает консервативный допуск, а не автоматическое восстановление повреждённых данных.

### Имена и порядок

| Шаг | Файл | Предлагаемое полное имя результата |
|---|---|---|
| 1 | `01_purchase_events.sql` | `lakehouse.stage.night_case1_purchase_events` |
| 2 | `04_quality_checks.sql` | Проверочный SELECT, не отдельная запись |
| 3 | `05_pair_diagnostics.sql` | Проверочный SELECT / отдельный отчёт |
| 4 | `02_first_purchase.sql` | `lakehouse.mart.night_case1_first_purchase` |
| 5 | `03_winrate.sql` | `lakehouse.mart.night_case1_winrate` |

Имена одинаковы во всех зависимостях и не пересекаются с исходными `task/case1` таблицами. В поле имени таблицы портала обычно указывается только часть после слоя, но интерфейс нужно сверить с фактической версией портала.

### Что исправляет пакет

- Слой событий сохраняет **все имеющиеся RAW-строки itemid=164**, в том числе проблемные и вне периода. LEFT JOIN с заранее проверенной уникальностью не размножает события. Проблемы представлены отдельными `dq_*` флагами, исходные причины можно исследовать без восстановления догадками.
- ID события проверяется по всей RAW-коллекции, чтобы конфликт ID с другим предметом также исключал пару. NULL ID и любые повторы не разрешаются произвольным выбором строки.
- Для матча требуется ровно одна RAW-строка, для покупателя ровно одна строка аккаунта в матче и уникальный слот. Даже идентичные повторные строки исключаются консервативно до разбирательства. Выбор «последней» версии не применяется без согласованной семантики версий.
- Первая покупка публикуется только если **каждое доступное событие пары** валидно, а всего событий одна или две. Поэтому удаление плохой ранней покупки не превращает следующую в доверенную первую.
- Явный период по start_time матча в Unix-секундах: `[1791936000,1792108800)`, то есть 14.10.2026 00:00 UTC включительно — 16.10.2026 00:00 UTC исключительно. Неизвестная дата исключает пару из аналитики, но сохраняет событие в диагностике. Это не фильтр по времени покупки или загрузки.
- Аккаунт 0/отрицательный/NULL исключается. Аноним 4294967295 допустим только при однозначной привязке. NULL ранга сохраняется. Неизвестные режим, лобби, герой, сторона, исход и некорректное время препятствуют аналитическому допуску.
- Точная медиана строится после всех допусков, все равные порогу относятся к early. Итоговый эффект хранится в п.п. Пустая/одногрупповая выборка даёт NULL метрики, а не фиктивный ноль.
- `history_complete=NULL` и `is_provisional=TRUE` сохраняются явно: технические проверки не доказывают полноту истории относительно источника.
- Смешанные `stage_loaded_at` или `rules_version` в одном выходном слое блокируют публикацию первых покупок целиком. Это базовый предохранитель, не замена атомарному snapshot и независимой проверке источников.

### Проверка до публикации в кластере

1. Проверить реальные имена и типы `lakehouse.raw.pg__matches`, `pg__match_players`, `mongo__purchase_events`. Пакет использует только поля документированной предметной схемы, без неоднозначного loaded_at. Типы ID должны быть совместимы, времена — в секундах. Непарсящиеся строки следует направлять в quarantine на входе, а не молча приводить.
2. Зафиксировать неизменяемые входные Iceberg snapshots / экспорт трёх источников и сохранить их ID, период, число строк, контрольные суммы, правила выбора версии. Читать меняющийся общий RAW как три независимых текущих таблицы недостаточно для воспроизводимости. В пакете snapshot IDs не выдуманы и не зашиты.
3. Выполнить preview и полный запуск на Spark отдельно. Локальный SQLite-тест не проверяет диалект, типы, часовой пояс и оптимизатор Trino/Spark. Потребность в адаптации syntax/type casts должна быть проверена в реальной среде.
4. Сверить COUNT RAW itemid=164 со COUNT выходного слоя событий для **того же снимка**. Проверить уникальные/несопоставленные связи и каждую `dq_*` причину. Числа причин могут пересекаться, их нельзя суммировать в воронку потерь. Пары >2 событий остаются в `05_pair_diagnostics.sql`.
5. Проверить уникальность `(match_id,steam_account_id)` первых покупок и отсутствие допуска любой проблемной пары. Проверить единый порог и стабильную генерацию входа/выхода. При изменении STAGE пересобрать обе MART последовательно. Для глобальной блокировки публикации и alerts нужно добавить DQ gate в Airflow: SELECT сам по себе DAG не останавливает.
6. Сохранить итоговые полные выгрузки, run IDs/snapshot IDs и результаты проверок. Только после этого заменить в презентации статус «предложено/проверено локально» на фактический кластерный статус.

Требования паспорта, которые SQL не настраивает: часовой пересчёт при изменении источников, SLA, хранение проектного среза до защиты +30 дней, ограничение прав, согласованный retention и атомарная публикация цепочки. Внешние решения также нужны для подтверждения зачёта Доминатора как обязательного SQL-кейса и независимой оценки полноты истории.

### Локальная проверка на синтетических краях

```powershell
python night/analysis/case1_sql/verify_synthetic.py
```

Скрипт выполняет именно подготовленные SQL SELECT на синтетических таблицах SQLite в памяти. Меняет только полные имена таблиц на локальные. Никакие реальные таблицы не запрашиваются. Результат: `case1_sql/synthetic_check_report.json`.

Проверяются сохранение всех событий без размножения, исключение всей пары при NULL/отрицательном/слишком позднем времени, лимит >2, анонимы, конфликты match/slot/event ID, ID между разными предметами, границы периода, боты, пропуски контекста, неверный исход, неизвестный ранг, точная чётная/нечётная медиана и ничьи на пороге, общие матчи обеих групп, смешанные генерации, пустая и одногрупповая выборки. Синтетические винрейты из отчёта служат исключительно тестовыми ожиданиями и **не относятся к реальному кейсу**.

## Методика ML: peers, baseline и независимая проверка

### Единица и признаки

Единица модели — профиль аккаунта в заранее определённом временном окне, а не отдельная случайная строка одного и того же игрока. Пример признаков: число наблюдавшихся матчей в окне, винрейт, медианы KDA/GPM/XPM/урона в минуту и их разброс. Полную историю/малый стаж аккаунта нельзя установить по числу строк данного CSV. Метку smurf, ID аккаунта и собственный score не включать в признаки. Агрегаты должны использовать только прошлое относительно момента оценки.

### Группы peers

Сравнивать с сопоставимыми игроками: один контекст режима/патча, уровень матча и роль. Способ определения роли/уровня и минимальный размер группы требуется согласовать по доступным источникам. Ранг неизвестен у всех текущих кандидатов, farm_pos пуст: их нельзя восстановить уверенным присвоением из GPM. Пока надёжных роли/уровня нет, peer-нормализацию следует считать незавершённой. Для редких групп заранее определить укрупнение/отказ от score и показывать недостаточность данных.

### Прозрачный baseline

Критерии кейса №18 предлагают KDA>5, GPM>700, winrate>65% при малом количестве игр и Isolation Forest. До запуска определить, чем агрегируются KDA/GPM и как задаются окно/«малое число игр». Сравнить модель с такой фиксированной эвристикой на одном holdout и при одном бюджете ручной проверки. Файл позволяет посчитать только описательные пороги строк: KDA>5 у 66/87, GPM>700 у 46/87, оба порога у 41/87. Это не количество подтверждённых смурфов.

### Isolation Forest

Собрать репрезентативные peer-профили, не обучать детектор только на текущих 6 выбранных аккаунтах. Пропуски и масштабирование согласовать заранее. Обучить Isolation Forest, зафиксировать seed, признаки, окно, версии библиотек, hyperparameters и convention score. Порог/contamination выбирать на train/validation и по бюджету проверки, а не по максимальному результату holdout. Возвращать anomaly score, peer-группу, число наблюдений и признаки отклонения. Высокая аномальность требует ручной проверки альтернативных объяснений.

### Holdout по аккаунту и времени

Все строки одного аккаунта принадлежат одной части train/validation/test. Для будущего сценария использовать более позднее окно как временной holdout и не допускать будущие матчи в признаки. Проверять account overlap=0, границы времени и отсутствие меток/score в признаках. При шести аккаунтах нынешнего файла и отсутствии контроля содержательная оценка не получится: сначала нужен расширенный набор. Если оценка предполагает известных аккаунтов в будущем, это отдельный сценарий и отдельная временная проверка, не замена независимому тесту на новых аккаунтах.

### Метрики

При независимо проверенных положительных и отрицательных метках: precision@K для бюджета ручной проверки, precision/recall с доверительными интервалами, доля false positives по peers. Разметчики должны проверять профиль независимо от model score. При отсутствии подтверждённого gold standard показывать долю проверенных кандидатов, стабильность score и качество данных, не называть это точностью обнаружения смурфов. В текущем CSV все метки равны 1 и их происхождение неизвестно, поэтому supervised-метрики не рассчитываются.
