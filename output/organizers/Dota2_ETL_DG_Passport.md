## 2 Логика ETL и аналитический контракт

### Подготовка STAGE

Матчи: выбирается последняя версия по loaded_at; точные повторы схлопываются. Если у последней версии одного match_id остаются разные записи, ключ исключается. Режимы 15, 18, 19, 20, 21, 23 и лобби 1, 4, 8 исключаются. Значения NULL режима и лобби сохраняются. Проверки положительной длительности в сохранённом SQL нет. [5]

Участники: ROW_NUMBER оставляет одну запись на (match_id, player_slot) с приоритетом src_modified_stamp и дополнительных полей. Покупки: поля приводятся к типам, точные повторы удаляются; конфликтующие версии одного id исключаются. В обоих запросах есть соединение со stage.matches. Это имя отличается от stage.matches_fixed в MART; соответствие объектов требуется сверить с фактическим DAG. [5]

### Преобразование dom_buyers

| Шаг | Фактическое правило SQL |
| --- | --- |
| 1 buys | itemid = 164 и time >= 0; MIN(time) по (match_id, steam_account_id) |
| 2 players | account_id IS NOT NULL и account_id <> 4294967295; одна строка на (match_id, account_id) по минимальному player_slot |
| 3 j | INNER JOIN с matches_fixed по match_id; LEFT JOIN с players по матчу и аккаунту |
| 4 med | approx_percentile(buy_time, 0.5) по строкам is_direct |
| 5 результат | resolution = direct при найденном участнике, иначе hidden; медиана добавляется ко всем строкам через CROSS JOIN |

### Метрики и правила использования

Для direct признак is_early равен buy_time <= median_buy_sec. Для hidden поля win и is_early равны NULL; такие строки не включаются в сравнение винрейтов. Основная метрика — 100 × (винрейт ранней группы − винрейт поздней группы), в процентных пунктах. Знаменатель — покупатели в матчах, а не уникальные матчи. Цель паспорта кейса: не менее +3 п.п. [1, 4, 6]

Медиана общая для прямых сопоставлений витрины; при фильтрации графиков её не следует заменять медианой каждой подгруппы. Равные порогу времена относятся к ранней группе. Период кейса заявлен как 14–15 октября 2026 UTC; текущий SQL MART не фильтрует start_time и сам этот период не подтверждает. [4, 6]

## 4 Data Governance и качество данных

### Правила, подтверждённые сохранённым кодом

Покупки предмета 164 с отрицательным или NULL time не участвуют в расчёте. При повторных покупках используется минимум оставшихся времён. Несопоставленные покупки сохраняются для контроля покрытия. Значение resolution = hidden означает отсутствие прямого соответствия в SQL и не доказывает причину анонимности аккаунта. [4]

### Уточнения к исходному описанию

| Область | Состояние и влияние |
| --- | --- |
| Аккаунты | Описание new заявляет исключение NULL, 0 и 4294967295. SQL фильтрует только NULL и 4294967295 в players. В buys эти фильтры отсутствуют; account_id = 0 может получить direct. |
| Однозначность | ROW_NUMBER выбирает минимальный слот аккаунта. Если аккаунт встречается в нескольких слотах, выбор строки не подтверждает однозначную связь. |
| Предел времени | Проверки buy_time <= duration нет. При отрицательном событии и положительном событии пары сохраняется положительное; паспорт кейса требует исключать всю пару. |
| Число событий | Правило исключения пары с более чем двумя событиями Доминатора из паспорта кейса в SQL MART не реализовано. |
| Исход и NULL | Для direct значение p.win = NULL попадает в ELSE 0. При NULL duration получается последний dur_bucket, поэтому нужна отдельная проверка пропусков. |
| Ранг | Формула league подтверждена кодом. Соответствие диапазонов rank_raw названиям рангов из исходного текста отдельно не проверено. |
| Аудит и перезапуск | job_id и временные метки заявлены в DDL. Их заполнение, режим записи, инкременты и идемпотентность не подтверждаются одним SELECT. |

### Контроль качества при следующей загрузке

Рекомендуемые проверки: уникальность ключа результата; число NULL и нулевых аккаунтов; доля hidden; число строк с win IS NULL среди direct; время за пределами матча; конфликты аккаунтов по слотам; число исключённых пар и покрытие периода. Пороговые значения и поведение DAG при нарушении пока не согласованы. Это требования к контролю, а не отчёт о пройденных проверках. [4–6]

## 7 Контракт командной витрины

| Поле или группа | Содержание |
| --- | --- |
| match_id, is_radiant | Логический ключ: матч и сторона |
| win | Максимум индивидуальных флагов победы команды |
| duration, game_mode, lobby_type | Атрибуты матча из matches_fixed |
| dur_bucket | Те же интервалы длительности, что в dom_buyers |
| players_in_slots | Количество различных слотов стороны; допускается 5 |
| hidden_players | Число строк с NULL / 4294967295 account_id |
| dom_cnt | COUNT(dp.buy_time) после соединения участников и событий предмета 164 |
| team_has_dom | dom_cnt > 0 |
| first_dom_time | MIN времени события покупки в команде |
| match_has_hidden_buyer | Константа false в финальном SELECT |

### Ограничения интерпретации

dom_cnt считает события с заполненным buy_time, включая 0, а не уникальных покупателей. Повторные покупки одного игрока увеличивают показатель. В командном SQL нет фильтра time >= 0 или проверки времени относительно duration, поэтому first_dom_time может отличаться от минимального времени основной витрины. [4]

match_has_hidden_buyer всегда равен false в коде. Поле не является самостоятельной проверкой всех несопоставленных событий покупок: исключение bad_matches основано на участниках, а не на полном покрытии purchase_events_new. Аналогично, MAX(win) и проверка суммы командных побед не устанавливают согласованность каждого участника с radiant_win. [4]

### Назначение двух витрин

dom_buyers отвечает на вопрос о времени первой покупки у покупателя и его исходе. team_dominator_stats позволяет сравнивать наличие предмета у стороны и длительность матча. Сравнение «есть предмет / нет предмета» не заменяет сравнение ранней и поздней покупки. Наблюдаемые зависимости не устанавливают причинное влияние предмета на победу. [4, 6]

### Проверка для организаторов

Полный SQL командной витрины доступен в task/case1/mart/team_dominator_stats.sql. В данном документе он представлен контрактом полей и отдельным исходным lineage, чтобы не смешивать его с основным SQL dom_buyers. [4]

## Приложение А Декларация схемы

Ниже приведён DDL из исходного паспорта без комментариев полей; их смысл раскрыт в словаре данных. DDL сохраняет типы источника и не заявляется как проверенный скрипт развёртывания. Для исполнения нужно выбрать диалект и определить параметры Iceberg и location. [1]

```sql
CREATE TABLE lakehouse.mart.dom_buyers (
  match_id bigint,
  steam_account_id bigint,
  buy_time integer,
  resolution varchar,
  player_slot integer,
  hero_id integer,
  rank_raw integer,
  league integer,
  is_radiant boolean,
  win integer,
  duration integer,
  game_mode integer,
  lobby_type integer,
  dur_bucket varchar,
  buy_bucket varchar,
  median_buy_sec integer,
  is_early boolean,
  job_id STRING,
  sys_insert_stamp TIMESTAMP,
  src_modified_stamp TIMESTAMP
);
```

### Сопоставление DDL и SELECT

DDL содержит 20 полей, SELECT возвращает 17 бизнес-полей. job_id, sys_insert_stamp и src_modified_stamp должен заполнять внешний механизм записи либо дополнительная проекция. Такого механизма в переданном SQL нет. Наличие аудиторских колонок в декларации само по себе не подтверждает инкрементальную или идемпотентную загрузку.

approx_percentile не приведён явно к integer, хотя median_buy_sec объявлен integer. Перед публикацией следует сверить тип результата с движком и фактической Iceberg-схемой. Первичный ключ, партиционирование и политика эволюции схемы в исходном DDL не заданы.

## Приложение Б SQL основной витрины

Часть 1 из 2. Исходный SQL из раздела 5 new/task.txt. Случайный повтор фрагмента запроса перед разделом 5 исключён; логика полного запроса сохранена. Это SELECT-преобразование без команды записи и без заполнения системных полей. [1, 4]

```sql
WITH buys AS (
    SELECT match_id, steam_account_id, MIN(`time`) AS buy_time
    FROM lakehouse.stage.purchase_events_new
    WHERE itemid = 164
      AND `time` >= 0
    GROUP BY match_id, steam_account_id
),
players AS (
    SELECT match_id, account_id, player_slot, hero_id, `rank` AS rank_raw, is_radiant, win
    FROM (
        SELECT mp.*,
               row_number() OVER (
                   PARTITION BY mp.match_id, mp.account_id
                   ORDER BY mp.player_slot
               ) AS rn
        FROM lakehouse.stage.match_players mp
        WHERE mp.account_id IS NOT NULL
          AND mp.account_id <> 4294967295
    )
    WHERE rn = 1
),
j AS (
    SELECT b.match_id,
           b.steam_account_id,
           b.buy_time,
           p.player_slot,
           p.hero_id,
           p.rank_raw,
           p.is_radiant,
           p.win,
           (p.match_id IS NOT NULL) AS is_direct,
           m.duration,
           m.game_mode,
           m.lobby_type
    FROM buys b
    JOIN lakehouse.stage.matches_fixed m ON m.match_id = b.match_id
    LEFT JOIN players p
      ON p.match_id = b.match_id AND p.account_id = b.steam_account_id
),
med AS (
    SELECT approx_percentile(buy_time, 0.5) AS median_sec
    FROM j
    WHERE is_direct
)
```

## Приложение Б SQL основной витрины

Часть 2 из 2. Продолжение того же запроса. [1]

```sql
SELECT j.match_id,
       j.steam_account_id,
       j.buy_time,
       CASE WHEN j.is_direct THEN 'direct' ELSE 'hidden' END AS resolution,
       j.player_slot,
       j.hero_id,
       j.rank_raw,
       CASE WHEN j.rank_raw IS NULL OR j.rank_raw = 0 THEN 0
            ELSE CAST(floor((j.rank_raw - 1) / 10.0) + 1 AS integer) END AS league,
       j.is_radiant,
       CASE WHEN NOT j.is_direct THEN NULL
            WHEN j.win THEN 1 ELSE 0 END                             AS win,
       j.duration,
       j.game_mode,
       j.lobby_type,
       CASE WHEN j.duration < 1800 THEN '1: <30 min'
            WHEN j.duration < 2400 THEN '2: 30-40'
            WHEN j.duration < 3000 THEN '3: 40-50'
            ELSE '4: 50+' END                                        AS dur_bucket,
       CASE WHEN j.buy_time < 360  THEN '1: <6'
            WHEN j.buy_time < 480  THEN '2: 6-8'
            WHEN j.buy_time < 600  THEN '3: 8-10'
            WHEN j.buy_time < 720  THEN '4: 10-12'
            WHEN j.buy_time < 900  THEN '5: 12-15'
            WHEN j.buy_time < 1200 THEN '6: 15-20'
            ELSE '7: 20+' END                                        AS buy_bucket,
       med.median_sec                                                AS median_buy_sec,
       CASE WHEN j.is_direct THEN j.buy_time <= med.median_sec END   AS is_early
FROM j
CROSS JOIN med;
```
