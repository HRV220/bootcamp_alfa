# Паспорт кейса 1: время покупки Доминатора и винрейт

**Цель:** проверить, выше ли винрейт команды покупателя при ранней первой покупке Доминатора.

**Гипотеза:** среди покупателей Доминатора винрейт команды при первой покупке не позже медианного времени выше, чем при покупке позже медианы.

| Параметр | Определение |
|---|---|
| Предмет | Helm of the Dominator, `itemid = 164` |
| Единица анализа | Один покупатель в одном матче; учитываем только первую покупку |
| Порог группировки | Нужно рассчитать медиану времени первых покупок на окончательной очищенной выборке, по одной строке на `(match_id, steam_account_id)`, после всех проверок и фильтров |
| Ранняя группа | Время первой покупки не больше рассчитанной медианы |
| Поздняя группа | Время первой покупки больше рассчитанной медианы |
| Наблюдение внутри матча | От начала до завершения матча; исход — победа команды покупателя |
| Период данных | Матчи 14–15 октября 2026 года по времени начала в UTC: с 14.10.2026 00:00 включительно до 16.10.2026 00:00 исключительно. Других дат матчей в доступных данных нет |
| Фильтр лобби | Исключаем матчи с `lobby_type IN (1, 4, 8)`; строки с NULL проверяем отдельно |
| Фильтр режима | Исключаем матчи с `game_mode IN (15, 18, 19, 20, 21, 23)`; строки с NULL проверяем отдельно |
| Фильтр аккаунта | `0` — бот, исключаем покупателя. `4294967295` — анонимный игрок, автоматически не исключаем: нужна однозначная связь покупки с участником и его стороной. NULL проверяем отдельно |
| Число покупок | Если у пары `(match_id, steam_account_id)` больше 2 событий Доминатора, исключаем всю пару из первых покупок. Это эвристика подозрения на бота; другие покупатели матча сохраняются |
| Ранг | По пояснению пользователя, NULL — игрок без ранга/на калибровке. Сохраняем его; ранг не используется как фильтр или условие основного сравнения |
| Глубина данных | Весь доступный срез матчей за 14–15 октября и связанные участники/покупки |
| Срок хранения | До конца буткемпа и ещё 30 календарных дней после защиты — для повторной проверки результата |
| Частота обновления | Требование: пересчёт раз в час при изменении входных данных. Для неизменного среза достаточно первоначальной сборки |
| Метрика группы | Винрейт = число побед / число наблюдений в группе |
| Основная метрика | Разница винрейтов: ранняя группа минус поздняя, в процентных пунктах |
| Целевой порог | **Не менее +3 п.п.**, например 53% против 50% |

**Критерий успеха по целевой метрике:** разница винрейтов составляет не менее +3 п.п. Статистическую уверенность в результате оцениваем отдельно; метод определим до проверки гипотезы.

**Кейс выполнен**, когда подготовлены проверенные данные, воспроизводимо рассчитаны метрики и их неопределённость, сделан вывод о достижении порога. Отсутствие подтверждения гипотезы тоже является допустимым результатом.

## Ограничения

- Доступны только матчи 14–15 октября 2026 года. Выводы относятся к этой выборке и не переносятся автоматически на другие периоды.
- Сравниваем покупателей Доминатора в разрешённых режимах и лобби. Пользу покупки относительно игры без предмета не оцениваем.
- Покупки без однозначной связи с матчем и участником исключаются из анализа. В прежнем срезе это 19,4% пар до фильтров; такие потери могут менять состав выборки.
- Анонимного игрока сохраняем только при однозначной привязке покупки. Общий ID анонимов не позволяет восстановить владельца покупки догадкой.
- Группы могут различаться героями, уровнем игроков и уже имеющимся преимуществом. Ранг не является фильтром; обнаруженная разница винрейтов не доказывает причинного эффекта ранней покупки.
- Поздняя покупка возможна только в достаточно длинном матче. Состав ранней и поздней групп поэтому может различаться по длительности матчей.
- Покупатели одного матча зависимы, в том числе на противоположных сторонах. Это нужно учесть при оценке статистической неопределённости.
- Исключение пар с более чем двумя событиями покупки — эвристика, а не доказанное обнаружение ботов. Проверены имеющиеся события RAW; полнота относительно источника независимо не подтверждена.

Правило порога определено заранее: медиана времени первых покупок на окончательной очищенной выборке. Численное значение нужно рассчитать и сохранить до сравнения винрейтов. Для чётного числа наблюдений медиана — среднее двух центральных времён; для нечётного — центральное время. Все покупки с временем, равным медиане, относятся к ранней группе, поэтому группы могут различаться по размеру. Порог единый для всего зафиксированного среза; при фильтрации графиков его не пересчитываем. Для завершения критерия №2 не требуется запускать ETL или проверять гипотезу.

**Проверено по результатам пользователя:** 17 863 покупки Доминатора, 17 781 пара «матч–покупатель». Уникальность основных ключей подтверждена. Однозначно связаны 14 332 пары; у 3 449 (19,4%) не найден матч или участник. Среди связанных событий время корректно относительно длительности матча, исходы согласованы. До фильтров неизвестен ранг у 5 318 связанных пар (37,1%).

**Дополнительная проверка текущего RAW:** матч найден, но участник не найден у 3 397 пар. У 14 пар в матче вообще нет строк участников; у 3 383 пар в матче есть анонимные игроки. Анонимизация — вероятное объяснение второй группы, но принадлежность покупки конкретному анонимному игроку не установлена. Это количество пар до фильтров режима/лобби, не число уникальных матчей. Результат не смешиваем с числами прежнего среза.

**После фильтров лобби и режима:** предварительно 11 797 наблюдений в 10 673 матчах. Среднее наблюдаемое время — 13 мин 28 с, медиана — 10 мин 15 с. Это результаты профилирования на прежних снимках, а не утверждённый порог. Нужно заново рассчитать медиану на окончательной очищенной выборке и определить размеры групп относительно неё; SQL-процессы ниже читают текущий RAW.

**Статус критерия №2:** источники, ключи, связи, результаты проверок, правила преобразования, глубина и частота обновления описаны. Неразрешённые связи сохраняем в диагностике и не включаем в первые покупки; других покупателей матча сохраняем. NULL ранга не является блокирующей проблемой. Ограничения: короткий период, часть покупателей не сопоставлена, полнота исходной истории независимо не подтверждена. Вывод будет относиться к доступной выборке. Процессы на сайте пользователь ещё не создавал; запуск относится к критерию №3.

Требование хранения относится к проектному срезу исходных данных, подготовленным таблицам и отчётам проверок. Фактическую настройку хранения и расписания реализуем на этапе №3; политики общего RAW здесь не меняем.

## Условия RAW → STAGE

- Берём только Доминатор `itemid = 164` из четырёх RAW-таблиц. Общие источники не меняем. SQL-процесс читает текущие данные, а не зафиксированные снимки прежней проверки.
- Исключаем из первых покупок лобби 1, 4, 8; режимы 15, 18, 19, 20, 21, 23; ботов с аккаунтом 0. NULL режима/лобби и некорректные ключи оставляем в диагностике.
- `4294967295` — анонимный игрок. Сохраняем его при однозначной связи с участником и стороной; нескольких анонимов в одного покупателя не объединяем.
- У события должен быть уникальный ID, у матча — уникальный `match_id`, у участника — уникальный `(match_id, player_slot)`. Нарушения помечаем в диагностике, такие пары не попадают в первые покупки. Строку произвольно не выбираем.
- Для допуска нужны ровно один матч и один участник, известные герой, сторона и исход. `win` сверяем с `radiant_win`. `rank = NULL` сохраняем с отдельным признаком.
- Время покупки используем в секундах по контракту RAW. Абсолютное время сохраняем как Unix-секунды (`match_start_epoch_sec`, `purchase_epoch_sec`), чтобы SQL не зависел от часового пояса preview и Spark. Пропуск/отрицательное время, неположительная длительность и покупка после окончания матча — причины диагностики.
- Если хотя бы одно событие пары проблемное, её первую покупку не публикуем как достоверную. Все исходные события Доминатора сохраняем в STAGE с причинами, даже если они исключены из первых покупок.
- При числе событий Доминатора больше 2 на игрока в матче исключаем всю пару. В событиях сохраняем количество, `exceeds_purchase_limit` и причину `excessive_purchase_events`. Одна или две покупки допустимы; бот по одному этому правилу не считается доказанным.
- В допущенных парах берём `min(time)`. Для аналитической группировки нужно рассчитать медиану этих первых времён после всех проверок и фильтров: `early` — время не больше медианы, `late` — больше. В текущем SQL этот расчёт выполняется в MART перед сравнением винрейтов.
- История пока не подтверждена: первые покупки помечаем предварительными (`is_provisional = true`, `history_complete = NULL`). Отсутствующие связи не восстанавливаем догадками.
- Полную замену Iceberg-таблицы и запуск через Airflow выполняет портал. Две таблицы создаются отдельными процессами: сначала события, затем первые покупки. Портал определяет зависимости по полным именам входов. При сверке проверяем `source_stage_loaded_at`; общая транзакция двух таблиц не предполагается.

## Как создать STAGE на сайте

В разделе разработки выбери слой **STAGE**, режим **SQL**. В поле имени указывай только имя таблицы без `lakehouse.stage`. В поле SQL вставляй файл целиком: один `WITH/SELECT`, без Python, `CREATE TABLE` и `LIMIT`.

По справке установленного портала preview работает через Trino, а Airflow выполняет запрос через Spark и создаёт Iceberg-таблицу. Поэтому запросы используют общий SQL-синтаксис без Spark-only функций и команд управления сессией.

1. Имя `case1_dominator_purchase_events`, SQL — [stage_purchase_events.sql](stage_purchase_events.sql). Проверь preview, создай процесс и дождись успешного заполнения таблицы.
2. Имя `case1_dominator_first_purchase`, SQL — [stage_first_purchase.sql](stage_first_purchase.sql). Создавай после первого процесса: запрос зависит от его STAGE-таблицы.
3. После успешного заполнения обеих таблиц выполни [stage_checks.sql](stage_checks.sql) как проверочный SELECT/preview. Отдельный процесс для проверок не нужен.

Контрольный ориентир старого среза — 17 863 события и 11 797 первых покупок. На текущем RAW объёмы могут измениться; размеры ранней и поздней групп нужно рассчитать заново относительно медианы. Preview не заменяет проверку всей записанной таблицы. SQL сохраняет нарушения в диагностике и не прерывает DAG автоматически: если нужна блокировка публикации по DQ, её добавляют отдельно в Airflow.

**Статус ETL:** SQL — заготовка для критерия №3, процессы на сайте ещё не создавались. Перед запуском привести запросы к фиксированному периоду 14–15 октября, проверить аудит входных версий и реализовать требования хранения/обновления. SLA и фактические настройки портала/Airflow проверяются отдельно. Назначение таблиц — в [модели](data_model.md).
